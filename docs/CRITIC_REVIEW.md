# Критик целей и эксплуатации — ревью blueprint 0.2.0

Дата: 29 сентября 2026. Это **внутренний adversarial review проектного предложения тем же ассистентом**, не независимый аудит другим экспертом, не live-тест продукта и не сертификат качества.

## Verdict

**GO к узкому feasibility-пилоту; не GO к обещанию универсального автоконсьержа.** Ценность гипотезы высокая для заявленного использования: не генерировать достопримечательности, а сокращать неопределённость и ручную организацию. Главная недоказанная часть — доступность качественных данных в будущей среде.

## Найденные риски и внесённые изменения

| Риск исходной идеи | Чем плох | Решение в blueprint |
|---|---|---|
| «Топ-5 за десять минут в любой точке» | Давит на модель заполнять квоту непроверенным | До пяти; бюджет этапа; отдельные conditional и полезный partial |
| «Куча MCP всё решит» | Обёртка не создаёт прав, свежести и покрытия | A0; статусы docs_checked/live_not_tested; fallback |
| Дешёвый перелёт подменяет выгодный отдых | Багаж, аэропорты, ночь и риск съедают экономию | All-in + усилия + door-to-door + согласие на self-transfer |
| Большую группу считают умножением | Нет доказанной одновременной вместимости | Полный состав в quote; групповой/ручной запрос при лимите |
| «Эксклюзивность» становится собственной целью системы | Релакс проигрывает сложной конструкции | Пресеты; novelty=0 для релакса; обычный пакет может победить |
| Еноты выглядят сертификатом достоверности | Красивая уверенность скрывает пробелы | Отдельный редакционный слой; критичный unknown скрывает награду |
| Прозрачная формула создаёт ложную точность | Субъективные баллы выглядят измеренными | Rubrics/evidence/uncertainty, интервалы и sensitivity |
| Критик видит только рассказ автора | Повторяет его ошибочную рамку | Исходный brief/evidence, strongest alternative, операционный dry-run |
| Критики зацикливают ремонт | Время/деньги уходят на косметику | Два разных checkpoint, один repair на каждый, visible remaining gaps |
| Красивый guide переписывает факты | Визуал становится второй моделью истины | Одна принятая ревизия; шаблон/вычислитель при наличии, иначе сверка и честный статус проверки |
| PDF/приложение без сети обещает слишком много | Карты и live-цены зависят от внешней сети | Offline текст+адреса; явная граница внешних функций |
| Готовый fork экономит разработку, добавляет эксплуатацию | Собственный UI/data model, миграции, ненужные модули | Изучать/экспортировать, не форкать большой планировщик на старте |
| Самостоятельный агент видит токены и выполняет страницы | Утечки и prompt injection | Host-enforced permissions; исследование не меняет код и не покупает |
| Все советы «устаревают через месяц» | Смешаны метод, каталог и котировки | Раздельные устойчивые политики и динамические факты; on-use refresh |
| Упрощение превращается в бесконечный чат | Пользователь не получает законченный результат | Два ограниченных выхода, понятный next step, snapshot и финальный пакет; локальный A2 необязателен |

## Самая сильная альтернатива

Взять Wanderlog или TREK как бытовой органайзер, а поиск делать внешним сильным агентом. Это рационально, если пользователь прежде всего хочет групповые планы, импорт броней и карты. Для нынешней цели — сравнительные варианты, проверяемые компромиссы, анти-SEO discovery и собственный люксовый readout — рекомендуемая методика поверх обычного облачного чата точнее; локальная оболочка не обязательна. При изменении цели выбор следует пересмотреть, а не защищать собственную архитектуру из упрямства.

## Что остаётся недоказанным

1. Какие инструменты реально доступны локальному/облачному агенту пользователя, включая travel-inventory и региональные условия.
2. Укладывается ли качественный первый readout в желаемый latency/cost на сложной группе.
3. Даёт ли наш discovery ощутимо лучшие находки, чем обычный хороший prompt с тем же web-доступом.
4. Насколько часто пользователь действительно открывает детальный guide в поездке; длинный документ может оказаться лишним.
5. Достаточна ли выбранная runtime-изоляция; prompt сам по себе прав не ограничивает.

Это вопросы пилота A0–A3, а не повод добавлять ещё framework и абстракции.

## Kill / simplify criteria

Если проверка провайдеров постоянно требует ручного сложного доступа, оставляем assisted mode, урезаем обещание и не строим scraper farm. Если новый источник не улучшает решение, удаляем/паркуем его. Если красивый UI отодвигает первый реальный guide, делаем меньше экранов, не ослабляя смысл. Если два критика не находят материальных дефектов на разнообразных полевых кейсах, сокращаем глубину, но сохраняем контроль самых рискованных мест.

## Итог

Проект достоин запуска как **персональная машина подготовки отдыха**, а не как мини-Expedia. Две неустранимые обязанности остаются: добывать свежие данные и честно показывать неизвестное. Всё остальное следует подчинять полезности, а не архитектурной полноте.


## Адверсариальный проход по поправке cloud-first

Это повторное проектное self-review тем же ассистентом, не испытание поведения будущей модели.

| Проверенный конфликт | Исправление / остаточный риск |
|---|---|
| «Основной пользователь без Git», но README требует папку research | Самостоятельный ENOT_CHAT_START, snapshot в файле/чате; local-контракты отделены |
| «Два критика», но нет вызова субагентов | Два sequential evidence-based прохода; запрет на заявление независимого аудита |
| «Сначала топ-5», но длинный ответ делает ещё два бонуса и guide | Ceiling по presented IDs за цикл; PLAN только после выбора; новый набор через REFINE |
| «Параметры можно менять», но перенос забывает старые veto | Полный краткий brief, revision и карта зависимостей в snapshot |
| «Одинаковое качество» скрывает отсутствие inventory | Общие обязанности одинаковы; качество на сопоставимых данных — гипотеза A3; материальный gap всегда виден |
| «Машинные расчёты» обязательны, но code tool нет | Явная арифметика/повторная сверка, качественная sensitivity; не утверждать вычислительную проверку |
| «Красивый ZIP всегда», но host не создаёт файлы | Реальные отдельные файлы либо текстовая выдача; никаких мнимых download/HTML-preview |
| «У пользователя нет нужды понимать систему», но вводится capability onboarding | Внутренняя маленькая карта; user-facing — следствие для поездки, без аббревиатур |
| «Сохраняем всё в памяти», но новый чат другой | Явно выдаваемый snapshot и portable URL; новый чат читает его, не предполагает соседнюю историю |
| «Короткая суть», но риски убраны в детали | Три слоя чтения; все decision-critical риски остаются в первом |
| «Cloud без кода» становится вторым разошедшимся методом | Cloud starter обновляется вместе с общими policy/контрактами; проверка согласованности при выпуске |

**Сильнейший контраргумент:** одна модель может воспроизвести исходную ошибку, а закрытый/неполный источник не станет доступным от хорошей инструкции. Не компенсировать это маркетинговым обещанием «почти как независимые агенты». Нужны исходные evidence, контрпоиск, сквозная сверка ограничений, видимые пробелы и сравнение в пилоте.

**Confidence:** высокая в том, что снята архитектурная зависимость от Git/делегирования в спецификации; умеренная в практической достаточности протокола; равенство качества между средами и latency не измерены. **Вердикт: HANDOFF_READY к A0+A1, не production-ready.** Следующий шаг и ограниченный бюджет — DELIVERY_PLAN.
