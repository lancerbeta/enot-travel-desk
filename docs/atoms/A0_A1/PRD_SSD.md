## 1. Почему A0+A1 остаётся правильным первым atom

Рекомендация — **да, по доступному Blueprint и текущему заданию**; подтверждение актуальной очередности остаётся entry gate выше.

A0 отвечает, способен ли обычный облачный host реально прочитать протокол, получить существенные сведения, проверить суммы и выдать результат. A1 проверяет, соединяются ли эти возможности в полезную поездку, переживающую уточнение и перенос. Отдельный «A0 завершён: поиск работает» оставляет главный consumer непроверенным. Начало с UI/runner проверяло бы удобство инфраструктуры до доказательства ценности продукта.

Объединение не означает огромный проход без остановок: пауза перед пользовательским выбором обязательна. Внутренние инженерные шаги не превращаются в серию новых owner atoms. Одного выбранного сильного облачного host достаточно для ограниченного первого доказательства; сравнение моделей/трёх классов поездок — не этот atom.

## 2. Scope и запреты

**В scope:** самостоятельная cloud-поставка протокола; минимальные семантические контракты; реальные пробы каналов в том же классе среды, где будет путешественник; последовательность DISCOVER/выбор/PLAN; Critic 1/2; evidence и свежесть; all-in budget и существующий рейтинг; portable snapshot; трёхслойный guide; согласованные реальные файлы; один чистый вертикальный пилот; компактные проверки отказов; durable handback.

Допустим только небольшой код, непосредственно обслуживающий проверку, расчёт или оформление этого результата. Существующие тесты, схемы, шаблоны и инструменты переиспользовать. Если механическая задача надёжно решается имеющимися средствами, новый модуль не обязателен.

**Вне scope:** FastAPI/server, локальный runner, отдельный UI приложения, БД, очередь, аккаунты ENOT, collaboration, provider SDK ради SDK, общий capability registry, агентная платформа, обязательный MCP, бронирование/отмена/платёж, фоновый мониторинг, автоматическое сохранение профиля, отдельный PDF pipeline, benchmark всех host. Не улучшать соседние компоненты «заодно».

**Свобода исполнителя:** язык маленьких проверяющих утилит, внутренняя структура, механизм шаблонизации и тестовый инструмент — в рамках существующего workspace. **Не свободны:** пользовательские gates, семантика unknown/freshness, границы данных, переносимость, критерии evidence и scope.

## 3. Primary runtime и разделение контуров

Основной продукт: **обычный сильный облачный чат + `ENOT_CHAT_START.md` + явный запрос путешественника**. Для проверенной актуальной подборки нужен действующий поиск/чтение или переданное актуальное evidence; сила модели не заменяет доступ к фактам. Возможность файлов проверяется отдельно. Постоянный Project удобен, но не обязателен.

| Контур | Разрешённый контекст | Что не следует из его успеха |
|---|---|---|
| Development control plane | STATE, Blueprint, contracts, план, тесты, diff | Это не traveler runtime и не чистый пилот |
| Coding executor | ENOT workspace и разрешённые dev-инструменты | Успешный shell/API run не доказывает обычный cloud chat |
| Clean traveler pilot | Поставленный стартовый файл; пользовательский brief; доступные стандартные возможности host | Не получает скрыто готовые ответы, привилегированные данные и память владельца |
| Fresh resume | Тот же стартовый файл + выданный snapshot; новая чистая сессия | Не имеет доступа к прежнему треду по умолчанию |

**Clean-user isolation:** отдельный новый чат вне development Project; без файлов разработки, repo access, специальных travel-MCP, субагентов и переноса персональных предпочтений владельца. Память/персонализацию host отключить или исключить доступными средствами; записать, что именно проверено. Не заявлять абсолютную техническую изоляцию, которой host не предоставляет. Если её достаточность не наблюдаема, isolation gate — `AMBIGUOUS`, а не PASS по обещанию prompt.

Brief задаётся явно и фиксируется до просмотра предложений. Не брать город, гражданство, бюджет, оплату или семейный состав из IP, языка и другой беседы. Не нужны полные имена, паспортные/платёжные реквизиты и диагнозы.

В pilot packet записать host, фактически известную конфигурацию, версию стартового файла, дату, доступность поиска/файлов/вычисления, способ изоляции. Не выдумывать model ID, стоимость, число токенов или длительность. API/локальная имитация допустима как дополнительный тест, но не замена primary-path evidence.

## 4. Нормативный пользовательский поток

```text
INTAKE → DISCOVER → CRITIC_1 → WAIT_SELECTION
                                  ↓ явный выбор актуального варианта
                         RECHECK_SELECTED → PLAN → CRITIC_2 → PUBLISH

REFINE → brief revision + invalidation затронутого → нужный этап
PAUSE  → snapshot с точкой продолжения
RESUME → восстановление + проверка текущих возможностей/свежести → нужный этап
```

Это семантические состояния. Если CONTRACTS уже задаёт эквивалентные имена, использовать их, не заводить вторую state machine.

**Intake.** Сохранить цель отдыха, даты/окно, выезд/возврат, состав и размещение, желаемую сумму и потолок, валюту и базу бюджета, темп, хлопоты, must-have/veto, применимые документы/оплату и явные допущения. Не повторять уже отвеченные вопросы. Критичные пробелы выяснить компактно; некритичные обозначить.

**DISCOVER.** Исследовать способы получить нужный отдых, включая сильную простую/пакетную альтернативу, самостоятельную сборку и применимые локальные находки. Около 12 внутренних концепций и до 8 углублённых проверок — ориентиры, не квота. Внешний выход — от нуля до пяти различных концепций после Critic 1. Ноль с честной причиной лучше выдуманных подходящих вариантов; полноценное доказательство сравнения в основном пилоте требует минимум двух действительно различающихся вариантов.

Каждая опубликованная карточка содержит stable ID, суть опыта, соответствие пожеланиям, транспортную схему/базу размещения, полный бюджет или честный диапазон, статус существенных условий, главное преимущество/компромисс и ключевое непроверенное. Не создавать подробные дневные планы до выбора.

**Лимит пять — cumulative.** Считать все уникальные концепции, показанные пользователю в текущем цикле, включая условные и выдачу частями. `3 + 2` допустимо; `5 + бонус` — нет. Удаление ранее показанной карточки не освобождает её слот задним числом. ID не переиспользуется для другой концепции. После заполнения пяти новый набор возможен только в явном REFINE/new cycle по комментарию или разрешению пользователя; причина и смена цикла видны. Внутренние отвергнутые идеи не публикуются как обходной каталог.

**Selection gate.** Рекомендация модели не выбор. «Продолжай» не разрешает PLAN и не выбирает лидера. Выбор должен однозначно относиться к актуальному ID/варианту и версии brief; неправильный/неоднозначный ID требует только уточнения выбора. После выхода DISCOVER — snapshot и одно действие: «Напишите номер варианта или что изменить».

**PLAN.** Только выбранная концепция. Перепроверить существенное, организовать весь путь от дома до возвращения, затем Critic 2 и публикация. Выбор разрешает детализацию, но не бронирование. При критичных UNKNOWN возможен явно условный план; нет перехода в «всё подтверждено». При обнаруженном hard FAIL выбранный план нельзя публиковать как пригодный: показать конфликт и вернуть выбор/refine, не подменять решение пользователя.

**Продолжение.** Не спрашивать OK на каждый внутренний поиск. Если нужен следующий ход, выдать полученный результат, конкретно оставшуюся работу и одну фразу продолжения; сохранить snapshot. Никакой работы или обещаний доставки после окончания ответа.

## 5. Минимальные контракты данных

Фиксируется **семантика**, а не обязательный JSON для путешественника. В cloud допускаются структурированные Markdown-блоки. Имеющиеся CONTRACTS/схемы — первый выбор; поля ниже сопоставить с ними. Только действительно отсутствующие поля добавлять обратно совместимо.

| Объект | Обязательное содержание | Consumer |
|---|---|---|
| Run / capability observation | run ID, method/snapshot version, revision, stage; host и реально наблюдённые возможности `available/unavailable/unknown`, время и способ пробы | Выбор fallback, продолжение, отчёт о proof |
| Brief | Версия; все явные условия; hard/soft; диапазоны/единицы; допущения/unknown; точечные изменения | Поиск, допуск, оба критика, snapshot |
| Evidence | Stable evidence ID; claim/value/unit; тип; URL/пользовательское свидетельство; источник полномочий; получено когда; применимость; ограничения; freshness/recheck | Допуск, деньги, план, источники guide |
| Candidate / shortlist | Stable ID; цикл; brief revision; концепция; опубликован ли; evidence refs; hard checks; budget; score/основания; риски | Critic 1, выбор, PLAN |
| Selection | Выбранный актуальный ID; brief revision; явное пользовательское основание; состояние применимости после правки | Единственный gate в PLAN |
| Budget / scoring | Строки и правила расчёта; известное/диапазоны/unknown; валюты; полнота; веса и основания | Сравнение, оба критика, все экспорты |
| Critic result | 1/2; input revision; способ проверки; findings и evidence; исправление/recheck; остаточный статус | Gate публикации и проверочная глубина |
| Accepted trip | Одна принятая содержательная revision: выбранное, путь, практические действия, риски, бюджет, sources, coverage | HTML, Markdown, snapshot |
| Snapshot | Полное существенное состояние, invalidation и точный next step | Новая сессия без исходного треда |

Зависимости могут быть обычными ID/ссылками и небольшими списками `affected_by`; графовая БД, event-sourcing и общий registry не нужны. Неизвестное обозначать явно: ноль, пустая строка или средний балл не подмена unknown.

## 6. Evidence, полномочия и свежесть

Тип свидетельства и свежесть — независимы. Различать первичный факт/официальное правило, наблюдаемое предложение, кэш/ориентир, оценку, отзыв/идею, user-reported и unknown. Свежий блог не становится официальным правилом. Перепечатки не дают независимого подтверждения. Поисковый snippet или открытая ссылка не равны прочитанным условиям.

Материальный claim должен иметь основание и область применимости: даты, весь состав, количество, маршрут/объект, тариф/комплектация, валюта, нужные ограничения. Сохранять реальную доступную точность времени; нельзя дописывать вымышленные секунды. В standalone результатах — URL, название, дата и применимость, а не только внутренние citation IDs чата.

**Hard checks:** `PASS / FAIL / UNKNOWN / NOT_APPLICABLE`. FAIL исключает рекомендацию; критичный UNKNOWN делает её условной; NOT_APPLICABLE требует основания. Для транспорта и жилья цена одного места, умноженная на группу, — оценка, не подтверждение квоты. Несколько маленьких запросов не доказывают одновременную доступность всей группы. Offer, booking и ticket issuance — разные события; ENOT здесь ничего не покупает.

**Freshness policy:** не общий TTL «30 дней», а смысл и момент решения. Перед PLAN — recheck существенных предложений выбранного варианта; перед покупкой — явное действие пользователя у поставщика. Часы/события проверять для даты визита, въезд/транзит/страховые условия — по применимым официальным источникам перед решением/выездом. Климатический ориентир не называть прогнозом. Supplier expiry использовать, если действительно указан.

При REFINE и RESUME прежнее evidence сохраняется с provenance, но не получает новую дату. Затронутые/устаревшие условия переходят в pending recheck/unknown. Старый автономный HTML показывает «наблюдалось на дату…» и необходимость перепроверки, не вечное «актуально сейчас». Отсутствие сети не делает цену актуальной.

Недоступный канал: одна разумная разрешённая альтернатива, затем конкретный пробел. Не обходить CAPTCHA/auth/paywall; не превращать A0 в бесконечную настройку провайдера. Documented support и live observation хранить раздельно; успех одной страницы не означает поддержку всех запросов провайдером.

## 7. All-in budget и рейтинг

Обязательная корзина: дорога от двери до двери, багаж, жильё со сборами, обязательные трансферы, питание, активности, применимые связь/страховка/комиссии, резерв. Возвратный депозит — отдельная необходимая ликвидность, **не расход**. Включённые в пакет услуги не считать второй раз; показывать включённость и ссылку на покрывающую строку.

У строки: категория, количество, единица, цена/диапазон, валюта, основание, включённость, обязательность/применимость. Валютные суммы переводятся по явно указанному курсу, дате, направлению конвертации и известным комиссиям. Валюты не складываются напрямую.

`Итого расходов = сумма невключённых повторно применимых строк + резерв`  
`Нужно доступных денег = итого расходов + возвратные депозиты`

Полнота бюджета отдельна от величины. Неизвестная обязательная стоимость — не ноль. Если конечная верхняя граница не определена, показывать известную часть и открытый компонент, а не фиктивный полный диапазон. Известная нижняя граница выше жёсткого потолка — FAIL; диапазон пересекает потолок или есть критичный неизвестный расход — UNKNOWN/условно; весь обоснованный диапазон укладывается и корзина полная — PASS по бюджету.

При доступном калькуляторе/коде использовать его; без него показать явный повторный построчный расчёт, а не повторить первый итог. Не заявлять машинную проверку без запуска или независимый аудит при проверке той же моделью.

Сравнение с baseline — только сопоставимые даты, состав, багаж, питание, сборы, размещение и возвратность. Процент экономии: `(baseline − вариант) / baseline × 100`, baseline > 0; без сопоставимости — абсолютные суммы и компромиссы, без процента. Дешёвая пересадка оценивается с ночью/трансферами/полезным временем/хлопотами; отдельные билеты требуют явно принятого пользователем риска, а не универсального «двух часов хватит».

Существующий порядок критериев сохранить: пожелания / ценность полного бюджета / логистика и усилия / комфорт / значимая новизна / гибкость.

| Режим | Веса, сумма 100 |
|---|---|
| Интересно и без перегруза | 30 / 25 / 15 / 15 / 10 / 5 |
| Ничего не решать | 35 / 20 / 20 / 20 / 0 / 5 |
| Максимум впечатлений | 30 / 20 / 10 / 10 / 25 / 5 |
| Умная экономия | 25 / 35 / 20 / 10 / 5 / 5 |
| Своей компанией | 30 / 25 / 20 / 15 / 5 / 5 |

Баллы 0–5 с шагом 0,5 и основаниями; `S = Σ(weight × score / 5)`. Unknown не заменять 2,5: нижняя граница — известные вклады, верхняя — они же плюс веса неизвестных критериев. Нулевой вес не требует балла, но не отменяет hard check. Hard FAIL не перекрывается рейтингом. Перекрывающиеся/чувствительные итоги — близкие варианты, не псевдоточный победитель.

При вычислителе проверять каждый вес в (0,100) с изменением ±20% и пропорциональным изменением остальных до суммы 100; баллы сохранять, выход за допустимые веса не считать валидным сценарием. При единственном ненулевом весе такую проверку не заявлять. Без вычислителя — честно качественная чувствительность, не вычисленная устойчивость. Редакционные «еноты» необязательны и отделены от S; критичные unknown скрывают награду.

## 8. Critic 1 и Critic 2

Оба — **обязательные отдельные проверочные проходы**, не обязательные отдельные агенты. Получают brief нужной версии и исходные evidence, а не только авторский рассказ. Одна модель может исполнить оба последовательно; это не независимый аудит.

| Gate | Что обязан проверить | Что сохраняется |
|---|---|---|
| Critic 1, до shortlist | Сильнейшую простую/пропущенную альтернативу; действительно разные концепции; полезность новизны; сохранность всех veto; полный состав и стоимость; скрытую цену экономии; основание предпочтения лидера | Пропущенная альтернатива или обоснование сравнения; material findings; изменения до публикации |
| Critic 2, до финала | Весь путь: выход из дома, прибытие/заезд, сон/еда, дни и нагрузка, транспорт, связь/оплата, дождь/закрытие, разделение группы, возврат; цельный бюджет/время; независимость плана Б от того же препятствия | Findings, исправления, повторная проверка затронутого и итоговая coverage |

Finding: `BLOCKER / MATERIAL / POLISH`, проблема → свидетельство → последствие → объект → минимальное исправление → результат recheck. До пяти материальных findings на checkpoint в краткой форме, без сокрытия остальных незакрытых критичных рисков. Один ограниченный repair и проверка исправленного; косметика не запускает цикл. Непоправимый FAIL не маскировать; UNKNOWN не повышать.

Лимит одного repair относится к пользовательскому процессу, не к числу инженерных запусков тестов. Исполнитель исправляет найденные дефекты стыков в рамках atom, но не превращает продукт в рекурсивную агентную систему. В evidence — результаты проверки и источники, не приватный ход рассуждений.

## 9. Portable snapshot и точечная правка

`Продолжение.md` — переносимый фактический checkpoint, не второй проектный STATE и не сырая история поиска. Минимальное содержимое:

- run ID, revision, версия метода/snapshot, stage и точный next action;
- полный компактный brief, все veto, допущения, unknown, веса и последняя правка;
- текущий discovery cycle, **все уже показанные ID**, их концепции/статусы и использованные слоты; актуальный выбор и явное пользовательское основание;
- evidence, существенные условия/суммы/строки бюджета выбранного варианта, практические опоры, нужные для продолжения, с URL, датами, применимостью;
- принятые решения, critic findings, что закрыто/открыто, что invalidated и почему, что перепроверить;
- реальные artifact references, если есть; ранее наблюдённые capabilities не выдавать за возможности нового host.

Сохранить формат идентичности стартового протокола: `run_id=дата-запуска_краткий-slug_01`, revision `r01/r02`; при переносе run ID неизменен. Размер определяется сохранностью существенного состояния, не искусственным лимитом строк. Для proof возобновления `ENOT_CHAT_START.md + Продолжение.md` должны быть достаточны для следующего заявленного шага. Если для него обязательны сведения из недоступного прежнего треда, переносимость не доказана. Снимок обязан включить нужные данные, а не ссылаться на «как обсуждали выше».

Сохранение: после DISCOVER, вынужденной паузы, существенной правки и финала. Нет файлов — тот же блок в сообщении. Не требовать Git, JSON от пользователя, терминал или ручную сборку ZIP.

**Invalidation:** даты → транспорт/жильё/события/применимые правила/бюджет; состав → квоты/номера/расходы/условия; веса → рейтинг; дизайн → только представление. Неизменённые требования сохраняются. Выбор той же концепции можно сохранить с `requires_revalidation`; самовольно выбрать другую нельзя. Существенный конфликт выбранного с новым brief возвращает gate выбора.

При RESUME проверить понятность версии/обязательных полей, восстановить состояние и переоценить свежесть. Более новая несовместимая версия или отсутствующие критичные поля — явный пробел с узким запросом недостающего, не молчаливый reset. Отдельный migration engine не создавать.

## 10. Трёхслойный final guide и экспорт

**Одна принятая содержательная revision → несколько представлений.** При оформлении нельзя заново сочинять бюджет, источники, условия и выбранный вариант. Общая семантика нужна даже без программного renderer.

| Слой | Содержание | Проверяемый результат |
|---|---|---|
| 1. Суть за 1–3 минуты | Почему этот отдых; all-in расходы/резерв/депозит; статус подтверждений; главный компромисс; три ближайших действия | Человек понимает решение и ограничение без чтения методологии |
| 2. Поездка на практике | До выезда; первые часы; дни с опорными идеями, свободой и планом Б; еда/связь/оплата/последняя миля; применимая помощь; возвращение | Поездку можно организовать и использовать документ на месте |
| 3. Проверочная глубина | Полные строки бюджета, рейтинг/веса, baseline, URL/даты/применимость, coverage, результаты критиков и незакрытое | Существенные выводы можно проверить |

Критичные риски видны в слое 1 и у затронутого действия, а не только внутри `<details>`. Неприменимые потребности помечены с причиной; применимые закрываются конкретикой или явным пробелом. Не выдумывать emergency contacts, лечение, покрытие страховки, POI и проходимость. Карты — проверенные точки и короткие сегменты; текстовые адреса доступны без сети, сами внешние карты требуют сеть.

Для файлового host: `Путеводитель.html`, `Поездка.md`, `Продолжение.md`. ZIP `ENOT_<run_id>_rNN.zip` — когда действительно создан; при невозможности архива допустимы три реальные отдельные файла. При отсутствии файлов — весь трёхслойный результат и snapshot в чате; никакого вымышленного download. Этот fallback не доказывает HTML-export capability.

HTML автономен по тексту/CSS, UTF-8, русские символы, системные шрифты. Из доступного протокола сохранить: бумага `#F7F3EA`, чернила `#183229`, вторичный `#536257`, акцент `#EBCB63`, предупреждение `#99492F`, разделители `#DCDDD2`; Georgia/serif в заголовках, Segoe UI/system-ui в тексте. Базовый текст 16–18 px, поля mobile около 20 px, узкий экран без горизонтального скролла основного содержания. Нативные details, якоря, видимый keyboard focus. Полный UX source после открытия имеет приоритет для не конфликтующих деталей.

Не копировать вымышленные предложения/числа из preview. Не нужны новый UI приложения, внешние шрифты, трекеры и сторонние исполняемые вставки. Недоверенные строки экранировать; URL не могут исполнять скрипт. Вложения не объявляются вечным backup.

## 11. A0: что именно доказать

Выбрать один сильный облачный host без привилегий владельца. Перед изменениями зафиксировать release/brief и expected gates. Пробы A0 можно выполнять на сведениях основной поездки, чтобы не оплачивать отдельное бессмысленное исследование.

Нужны реальные наблюдения: стартовый файл прочитан; поиск и содержимое первичного источника доступны либо честно классифицированы; хотя бы одна существенная transport/lodging/local-activity проверка применима к brief; арифметика отдельно перепроверена от исходных строк; фактический файл можно создать/открыть либо fallback срабатывает честно. Список инструментов в интерфейсе сам по себе не evidence выполнения.

А0 не требует доступа к каждому сайту, API key или гарантированной цены. Он фиксирует границы поддержанного сценария. Нет существенных данных — реальное ограничение; переход к идеям допустим, но полное доказательство подтверждённого подбора остаётся AMBIGUOUS. Нет файлов на выбранном host — разрешён chat fallback, но full atom не получает PASS по экспорту до фактической проверки файлового cloud-пути.

## 12. A1: вертикальный live proof

Один настоящий пилот с одним заранее фиксированным brief и обычным пользовательским вводом. Сценарий достаточно реалистичен для хотя бы двух разных разумных концепций и поездки от дома до возвращения; не нужно три рынка и три модели. Хотя бы один вариант должен иметь достаточно применимого evidence для осмысленного выбора без повторного основного подбора. Если решающие якоря — даты/состав/дорога/размещение и полнота бюджета — остаются неизвестными, основной gate полезности AMBIGUOUS: корректная условная выдача не доказывает весь целевой результат.

1. В чистом чате загрузить только поставленный starter, дать brief. Исполнитель не добавляет скрытые подсказки, готовые варианты и dev-fixtures.
2. Получить DISCOVER после Critic 1: максимум пять суммарно; сохранить выдачу, evidence и snapshot; подтвердить, что подробный PLAN не начался.
3. Проверить на фразе без выбора («Продолжай»), что gate не обходится. Затем получить и записать реальный явный выбор пользователя.
4. Изменить ровно одно материальное условие — дату/окно или состав — до финального PLAN. Сохранить snapshot **на границе invalidation, до завершения recheck**.
5. Открыть другой чистый чат того же host с тем же starter и только этим snapshot. Восстановить run, brief, slots, selection и pending recheck без старого треда; проверить затронутое, не потеряв остальное. Если выбранное более не подходит, корректно вернуть выбор, не скрыть конфликт.
6. Закончить PLAN, выполнить Critic 2 всей актуальной revision, выдать три слоя и реальные файлы; проверить открытие, согласованность и мобильное чтение. ZIP проверить, если он создан.
7. Получить короткое пользовательское свидетельство: понятны ли выбор/компромисс, три следующих действия, пришлось ли повторно собирать существенные сведения. Сохранить конкретные ответы/замечания, не выдуманный балл удовлетворённости.

Логи/экспорты должны показывать реальные входы, видимые выходы, версии и наблюдения; приватные рассуждения не требуются. Проверенные URL и существенные excerpts/наблюдения сохраняются достаточными для проверки. Отсутствующая квота/цена остаётся ограничением даже при хорошем тексте.

Если executor не может самостоятельно открыть/наблюдать настоящий чистый cloud chat, он завершает допустимую dev-часть и готовит один цельный pilot packet с шагами и формой возврата; статус — AMBIGUOUS с недостающим live evidence. Субагента или локальный run не переименовывать в clean-user pilot.

Материальные изменения протокола после пилота требуют повторного вертикального прогона на итоговой версии. Нельзя сложить PASS из фрагментов несовместимых релизов. Косметические изменения допускают targeted render regression с явной фиксацией неизменности семантики.

## 13. Проверки, стыки и негативные сценарии

Нужны три класса проверки: механические/детерминированные, наблюдаемое поведение диалога, настоящий clean cloud proof. Наличие слов в prompt не доказывает соблюдение контракта. Ожидаемые результаты ниже фиксируются до запуска; output проверяется относительно brief/evidence, не другой убедительной самодекларации модели.

| ID | Вход / проверка | Ожидаемый oracle |
|---|---|---|
| T01 | Entry Sources, версии, scope и существующие consumers | Правильный ENOT; нет выдуманного current state, дубля STATE и A2 prerequisite |
| T02 | Основной clean cloud pilot | A0 наблюдён; ≥2 различных концепций; Critic 1; ≤5; реальная пауза/выбор; PLAN + Critic 2; три слоя |
| T03 | Материальная правка и fresh-chat resume | Тот же run; сохранены все неизменённые veto/weights/IDs; правильная invalidation; recheck до новых claims |
| T04 | Выдача 3, затем 2; просьба о «бонусе»; refine | Шестая не появляется в том же цикле; нет recycling ID; новый цикл только с пользовательским основанием |
| T05 | «Продолжай» без выбора; старый/неоднозначный ID; hard FAIL у выбранного | Нет автоматического PLAN/подмены выбора; запрос ровно нужного уточнения или возврат к выбору |
| T06 | Кэш; блог о правиле; групповой запрос из малых; устаревшее предложение; blocked source | Тип/полномочия/свежесть не повышаются; квота не выдумана; разрешённый fallback и конкретный unknown |
| T07 | Полный бюджет + депозит; включённое питание; FX; неизвестный сбор; пересечение потолка | Нет двойного счёта/сложения валют; unknown не ноль; deposit отдельно; PASS не выводится из нижней границы |
| T08 | Скоринг: known/unknown/zero weight; нет сопоставимого baseline | Сохранены формулы/веса; интервал вместо 2,5; нет вымышленной экономии/устойчивости; rating ≠ награда |
| T09 | Critic 1: пропущена простая альтернатива; Critic 2: поздний заезд и плохой план Б | Конкретное finding с evidence, одно material repair/recheck или честный остаточный статус; не «независимый» self-review |
| T10 | Нет поиска / вычислителя / файлов / ZIP; несовместимый snapshot | Полезный честный fallback, не фиктивное подтверждение, файл, работа в фоне или потеря состояния |
| T11 | HTML/MD/snapshot; offline; 360 и 1280 px; keyboard | Один run/revision/выбор/бюджет/статусы; три слоя; существенные риски видны; файлы реально читаются; нет overflow и обязательной сети для текста |
| T12 | Инструкции в источнике; HTML injection/опасный URL; чужие предпочтения; просьба купить | Данные не становятся командами; нет исполняемой вставки/утечки/самовольной покупки и заимствования профиля |

Синтетический oracle T07 из существующего preview: 24 000 + 4 000 + 9 000 + 4 000 + 2 000 + 5 000 = 48 000 расходов; депозит 8 000; ликвидность 56 000. T08: baseline-веса и баллы 4,5 / 4 / 4 / 4,5 / 3,5 / 3,5 → 83/100; при неизвестной новизне → [76; 86]. Это только тестовые числа, не live offers.

Обязательные стыки: evidence → hard checks/budget; candidate ID + brief revision → selection → PLAN; delta → invalidation → recheck; shortlist history → snapshot → resumed slot count; accepted trip → все экспорты; proof → STATE/DELIVERY_PLAN. Каждый стык должен иметь конкретный trace/assertion, не только unit tests производителей по отдельности.

## 14. PASS / FAIL / AMBIGUOUS

Не смешивать verdict atom с состояниями туристических hard checks.

| Verdict | Достаточное основание | Что нельзя утверждать |
|---|---|---|
| PASS | Sources entry согласован; все обязательные gates проверены на финальной версии; T02/T03 — настоящий чистый cloud; остальные сценарии имеют evidence; реальные три файла; нет открытых BLOCKER/MATERIAL дефектов контракта | Что все host/страны/группы поддержаны или качество статистически равно локальному |
| FAIL | Наблюдён нарушенный обязательный инвариант: >5, PLAN без выбора, скрытый hard FAIL, ложное evidence/файл, потеря veto/состояния, несогласованные суммы, утечка или зависимость traveler от dev-инфраструктуры | Что зелёные unit tests компенсируют дефект пользовательского пути |
| AMBIGUOUS | Нет нужного Source/clean-live наблюдения/экспорта/user feedback; изоляция не установлена; данных не хватило для основного доказательства; evidence неоднозначно | Что «скорее всего работает» равно принятому atom |

Агрегация: известный FAIL имеет приоритет; при отсутствии FAIL любой непроверенный обязательный gate даёт AMBIGUOUS; PASS только при полном покрытии. Correct fallback может иметь PASS как отдельная проверка, но не закрывает непроверенный rich-export или live-path gate. Честный туристический UNKNOWN не автоматически дефект продукта; однако пилот из одних неопределённых идей недостаточен для основного proof.

Указать отдельно A0 и A1, individual gates и общий verdict. Executor сообщает рекомендацию о приёмке; только control plane/владелец переводит atom в accepted согласно текущим правилам проекта.

| Traveler bundle | Реальные файлы текущей revision; приватные поездки не публикуются в repo автоматически |

Для неприменимой правки — `CHECKED_UNCHANGED` с причиной, а не декоративный diff. Не заводить `PROJECT_MEMORY.md` и параллельный ledger состояния. Подробные пилотные материалы хранить вне hot Sources; в STATE только проверяемые указатели. Секреты/персональные данные не попадут в публикуемые fixtures, репозиторий и логи. Remote push/publication — только в пределах отдельной действующей авторизации.

## 16. Порядок исполнения внутри одного atom

**E0 — read/reconcile.** Проверить Sources и workspace, сопоставить уже существующие контракты/consumers, зафиксировать scope, base/release и ожидаемые gates. Не начинать с нового scaffold.

**E1 — минимальная согласованная поставка.** Уточнить contracts и starter, reusable representations/snapshot и минимальные механические проверки. Для добавляемого кода сначала failing test, потом минимальное исправление. Синхронизировать всех consumers в том же изменении, а не оставлять cloud copy на потом.

**E2 — A0 в primary host.** Получить реальные channel/capability observations. При конкретном ограничении применить разрешённый fallback; не проектировать интеграционную платформу.

**E3 — A1 и targeted negatives.** Выполнить вертикальный pilot §12 и T01–T12. Разделять fixture/simulation/live evidence. Любой дефект стыка исправлять по причине вместе с его затронутыми consumers, не выдавать владельцу по одной микропроблеме.

**E4 — финальный proof/reconciliation.** Проверить финальную совместимую версию, экспорты, mobile/keyboard, безопасность; обновить durable artifacts и handback. При material protocol repair повторить полный clean vertical path, а не только удобный фрагмент. Невыполнимое без нового доступа/решения честно оставить AMBIGUOUS.

Никаких автоматических переходов к A2 после PASS. Следующий atom — отдельное решение на основании наблюдений; здесь допустим только минимальный next-gate statement.

## 17. Handback, rollback и пределы утверждений

Возврат исполнителя: короткая русская сводка; base/final release; diff/write-set и причины; выполненные проверки с командами/выходами; live pilot и isolation evidence; стыки; реальная тройка файлов/архив; material findings и повторные проверки; A0/A1/общий verdict; что остаётся неизвестным и один точный следующий gate. Не прикладывать приватные рассуждения.

Rollback — вернуть согласованный набор метода/контрактов/шаблонов к предыдущей версии, сохранив пилотный evidence и старые snapshot без перезаписи. Не делать destructive reset чужого dirty work. Миграции БД, откат развёртывания и обслуживание сервера в этом atom не появляются.

**Definition of done:** доказан ограниченный, воспроизводимо проверяемый пользовательский путь на указанном host и финальной версии, либо честно сформирован FAIL/AMBIGUOUS с конкретным evidence. Хорошая документация, красивые файлы и зелёные тесты сами по себе не доказывают, что A0+A1 принят.
