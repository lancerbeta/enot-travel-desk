## 0. Решение и границы доказанного

Закончить сбор evidence текущего traveler smoke. Не продолжать живой поиск, не связываться с продавцами и не ждать покупки ради приёмки продукта. Наблюдалась цепь DISCOVER → выбор → PLAN/Critic 2 → HTML/snapshot → содержательное восстановление в новом чате. Это owner-runtime smoke на предложенном для проверки brief с живым исследованием, а не уже состоявшийся отпуск и не доказательство качества всех направлений.

Вердикт по текущей поставке — **REPAIR**: практическое восстановление прошло, но snapshot потерял часть контрактного состояния, а HTML не выполняет мобильный и трёхслойный контракт. Новые требования владельца расширяют содержание guide и уточняют финальную границу. Исторический PASS источников не отменяется. `COMPOSITION_FIRST_V1`, бюджетный evidence-kind experiment и A2 не включаются.

Один согласованный move состоит из двух последовательно выполняемых податомов:

| Податом | Outcome | Локальный gate |
|---|---|---|
| D1 — DIALOG_AND_HANDOFF | Одна полезная возможность уточнения, однозначное завершение на бандле, сохранённое состояние | Семантические regression checks и корректный snapshot round-trip |
| D2 — PRACTICAL_EDITORIAL_BUNDLE | Самодостаточный наглядный guide, фото, callouts, мобильная вёрстка и комплект | Проверка содержимого, реальный browser render и короткий вертикальный replay |

В DELIVERY_PLAN явно объединить D1+D2 этим move. Одновременно активен один податом. Перейти D1 → D2 можно после его локального gate по этой согласованной постановке; локальный gate не называется независимым PASS. Одна независимая приёмка всего move после handback. Не требовать нового OK между безопасными зависимыми шагами; при material conflict, нарушении прав или провале gate — остановить продвижение.

## 1. Основания

**FACT — Git:** STATE и DELIVERY_PLAN оставляют активным OWNER_REAL_TRIP_PILOT_V1. CONTRACTS уже задаёт Guide как единый смысловой источник, точный snapshot и независимость evidence/freshness. UX уже требует три слоя, мобильные карточки, текстовые адреса и источники изображений. Это не новая архитектура.

**FACT — артефакты smoke:** в snapshot признаны неизвестными прежний selection_cycle, candidate IDs и веса; версия метода не указана; stage/status не соответствуют каноническим перечислениям. В guide нет фотографий и native details; шесть таблиц требуют внутренней горизонтальной прокрутки на 390 px. Эти наблюдения проверены на загруженных файлах. Полный ZIP и Поездка.md не были предоставлены этой validation-сессии: их существование/согласованность независимо не подтверждены, но отсутствие не утверждается.

**FACT — код на базе:** `intake.py` хранит пропуски, но не выбирает за LLM вопросы; `snapshot.py` проверяет преимущественно наличие полей, не всю семантику; `render.py` — небольшой синтетический renderer с тремя выходами, а не полноценный шаблон фактически полученного cloud guide. Нельзя считать, что патч только Python изменит поведение облачного ЕНОТа.

**INFERENCE:** основной пробел находится на стыке метод → принятый смысл → публикация, а не требует нового поискового движка. Путь сохранения состояния нужно начинать в DISCOVER, не пытаться восстановить IDs из готового HTML.

**REFERENCE:** китайский HTML — только редакционный ориентир: обложка с фото, локальные примечания, карточки, смысловые подписи, раскрываемая глубина. Не копировать его личные данные, брони, file:// ссылки, 42 изображения, старые альтернативы, широкие таблицы, интерактивный бюджет или другой scoring. Права на повторное использование его фотографий не установлены.

## 2. PRD

### 2.1. Desired capability / consumers

Владелец описывает отдых обычными словами, при желании один раз дополняет пожелания, выбирает из максимум пяти разных концепций и получает качественный сохраняемый комплект, достаточный для самостоятельной организации и использования в поездке. Второй consumer — тот же или новый сильный облачный чат, которому пользователь позднее сам передаёт snapshot и вопрос.

Основной путь — сильный облачный чат с доступными актуальными источниками. Repo, Python, браузерные инструменты, apps/MCP/API и субагенты — необязательные усилители. Ни renderer, ни конкретный vendor не становятся prerequisite. Закупка/оплата остаются у владельца. Friend/cross-host distribution по-прежнему deferred.

### 2.2. Целевой разговор

`вброс → одно опциональное уточнение → DISCOVER ≤5 + Critic 1 → явный выбор → PLAN + Critic 2 → комплект → завершение`

Это целевой happy path, не обещание одинакового числа сообщений: material противоречие, настоящее ограничение host или неисполнимое требование могут потребовать адресного уточнения. Внутренние проверки, оформление и сравнение не создают отдельные approval gates. Реальные permission gates host сохраняются.

#### Одно опциональное уточнение — D1

При любом новом запросе сначала распознать уже сказанное. Проверить две категории пробелов: (а) выполнимость/бюджет/логистика, (б) существенное попадание в желаемый отдых. Богатый brief не означает, что уточнение запрещено.

Если полезные пробелы остались, до затратного поиска один раз предложить ответить на них **или продолжить как есть**. Обычно 2–4 коротких вопроса, не фиксированная анкета на 12 полей. При почти пустом запросе — существующие семь смысловых блоков, сгруппированные для одного ответа. Полностью достаточный brief не задерживать ради формы.

Пример, не текстовый тест: «Основное понял. Чтобы точнее попасть, можно добавить две вещи: насколько важен пляж прямо у отеля и нужен ли чемодан. Ответьте как удобно — или напишите “ищи так”, начну с тем, что есть».

Уточнять только ещё неизвестное. Не заставлять выбирать степень “самостоятельности”, если она уже ясна. Пропуск сохраняет null и `user_skipped`, а не неявное согласие. После отказа начать исследование без ещё одного OK. Если пользователь ответил только на часть и просит продолжать, предложенные, но не заполненные поля сохранить пропущенными. Не предлагать новые косметические вопросы после закрытия этого раунда, в том числе после resume. Явная исходная просьба «без вопросов / ищи так» закрывает раунд без навязывания формы. Новый material scope может потребовать ровно одного ставшего необходимым вопроса; это исключение, не новый общий intake.

Не выводить гражданство, город, оплату, состояние здоровья из языка/IP/смежных чатов. Не запрашивать персональные документы или реквизиты. Функциональные потребности (“избегать лестниц”) допустимы без диагноза.

#### Подбор и выбор

Максимум пять концепций суммарно за selection_cycle, включая conditional/withdrawn. Две или три сильные концепции — полноценный результат. До выбора: читаемые карточки в чате, all-in/статус, дорога, плюс/компромисс, существенный UNKNOWN. Полный HTML guide по всем вариантам не создавать. Стабильные IDs, preset/веса и brief фиксировать при первой публикации.

Рекомендация не является выбором. «Продолжай», сравнение двух вариантов и отрицательное упоминание кандидата не дают разрешение на PLAN. Не переписывать весь intent parser: обеспечить эту семантику в основном LLM path и существующих relevant seams.

### 2.3. Граница завершения — D1

Разделить два понятия, не строя новую машину состояний:

- **Комплект подготовлен:** данные и документы согласованы, понятны, сохранены доступным способом; существенные ограничения и действия владельца изложены.
- **Поездка куплена/условия подтверждены продавцом:** отдельное фактическое состояние, не следует из первого.

`stage=publish`, `status=ready`, `next_action=null` означает, что активная работа ЕНОТа завершена. Внутри guide остаётся `booking_tasks` — checklist владельца с дедлайнами, последовательностью и последствиями. Он не превращается в `status=needs_input` лишь потому, что покупка ещё не сделана или поздний заезд надо согласовать при бронировании.

Отдельного сервиса оплаты, booking assistant или сообщений продавцам нет. Готовые короткие запросы можно оставить в раскрываемой глубине; пользователь отправляет их сам. После финального сообщения не требовать прислать ответы отеля/билеты, не начинать мониторинг, не обещать продолжать в фоне. При инициативе пользователя — адресный Q&A / REFINE / RECHECK по snapshot.

**Это не способ скрыть плохой результат:** известный hard FAIL нельзя упаковать как пригодную поездку. Критичный неизвестный результат, способный обнулить выбранный отдых, виден в первом слое с условием/последствием и не превращается в “всё готово к оплате”. Доставить условный план разрешено с явной маркировкой; доказанного полностью пригодного варианта это не создаёт. Требования к истинности и admission не ослаблять.

Потенциальная смена рейса за два месяца, будущий ответ продавца и реальная покупка не обязаны происходить до выдачи документа. Уже доступный адрес/контакт/путь не следует отсылать на пользователя “узнаете на месте” без собственной разумной попытки проверки.

### 2.4. Полезное содержание guide — D2

Не справочник страны и не универсальная простыня советов. **Каждый раздел отвечает на конкретный вопрос путешественника**, факт привязан к объекту/сегменту/дате. Внутренняя карта покрытия ниже — не обязательные семь глав одинаковой длины.

| Момент | Минимально достаточная полезность |
|---|---|
| До покупки | Что покупать и в каком порядке; exact tariff/состав/налоги; отмена/оплата/валюта/депозит; что проверить до невозвратного действия; реальные ссылки |
| Дорога | Все местные даты и времена, нужный аэропорт/вокзал/терминал если подтверждён; сквозная/самостоятельная пересадка; багаж; действия после прилёта; последний участок до отеля; запас и вариант при сбое |
| Отель | Точное название, адрес текстом и map link; выбранный номер/кровать/питание; заезд/выезд в сопоставлении с рейсом; контакт/канал; полезные бытовые ограничения и что делать с ключами/багажом/едой при нестандартных часах |
| Повседневная жизнь | Как жить без машины, реальные пешие/транспортные опоры; еда с несколькими конкретными местами, географией и ценовой базой; вода/магазин/прачечная только где полезно; связь, активация, оплата и наличные |
| Отдых | Пляж/погода/сезон и их ограничения; 1–2 выбранных якоря; время/подвоз/сборы/одежда/физическая нагрузка; гибкий ритм; чем заняться при сбое без той же причины отказа |
| Безопасность и помощь | Применимые официальные правила и сроки; страховая/контакты помощи; локально важная безопасность; нужная одежда/зарядка/лекарства без назначения лечения и тревожного универсального списка |
| Возвращение | Ранний расчёт/ключи/завтрак, подача машины, подтверждённый канал и fallback, аэропортовый запас, багаж и домашняя последняя миля насколько заданы входы |

Для каждого существенного звена: **что → где/когда → как действовать → деньги/включённость → оговорка/план Б → источник и scope**. Это семантика, не шесть пустых полей в каждой карточке.

Не подставлять “15 минут пешком”, терминал, телефон, часы кухни или безопасный вход в море без подтверждения. Расстояние по прямой не равно пешему пути. Не обещать точную будущую цену меню. Текущие меню/публичные тарифы могут давать датированный ориентир; лимит путешественника обозначать лимитом. Нет подходящего evidence после разумного разрешённого чтения/fallback — кратко обозначить пробел и удобное действие, не заполнять уверенным текстом.

Отдельный внутренний проход перед финалом: доступный сейчас факт / требующий будущего recheck / ответ продавца или действие владельца / неприменимо. Первую категорию закрывать по возможности самим; остальные не превращать в бесконечное исследование. Это часть существующего Critic 2, не Critic 3.

### 2.5. Подача и 4–5 изображений — D2

**Слой 1, 1–3 минуты:** обложка, место/даты/состав/ритм, рабочий all-in и статус, резерв/депозит, главный компромисс, важные условия до оплаты, три ближайших действия владельца. Ясная фраза: “Комплект подготовлен. Бронирований нет”. Не использовать зелёный статус для неподтверждённой покупки.

**Слой 2:** несколько крупных разделов по задачам (“Дорога”, “Отель”, “На месте”, “Дни и впечатления”, “Если планы меняются”, “Домой”). Карточки с фактами и 0–2 содержательными callouts там, где уместно. Существенные предупреждения не ограничиваются квотой и не скрываются.

**Слой 3:** нативные details/якоря — бюджет по строкам, источники/свежесть, scoring/preset/основания выбора, findings Critic 1/2, короткие сообщения продавцам. Длинная история отвергнутых тарифов не повторяется в основном маршруте.

Три типа смысловых callouts достаточно: `important` (“До оплаты”), `tip` (“На месте пригодится”), `fallback` (“Если…”). Тип не обозначает доказанность: статус факта хранится отдельно. Пример: “Выезд в 05:00, раньше ресепшена. Рассчитайтесь вечером; выдачу/возврат ключей нужно согласовать. Пока не подтверждено”. Не писать “машина подтверждена” вместо “подтвердить машину”.

Фото — целевой стандарт **4–5 на весь выбранный guide**, не на каждый раздел и не на каждый shortlist-вариант. Рекомендуемые роли: обложка/контекст места, реальный пляж, выбранный объект (или номер только при доказанной категории), главное впечатление, необязательная локальная деталь. Распределить по смысловым разделам; без карусели, случайных stock-фото и дублей одного вида.

У фото: что изображено, исходный URL/автор, основание разрешённого использования, подпись/alt, область применимости (регион/объект/точная категория). Фото региона не выдаётся за пляж отеля; галерея отеля не гарантирует вид из выбранного номера. Сгенерированное изображение не заменяет документальную фотографию. Не снимать водяные знаки, не переносить чужие изображения из референса автоматически. Одной атрибуции недостаточно для утверждения разрешения на повторную публикацию.

Для типовой поставки подобрать подходящие изображения за ограниченный проход через доступные разрешённые источники. Если права/релевантность/доступ не установлены — изображение пропустить либо дать ссылку на оригинальную галерею, честно отразить ограничение. Не срывать полезную текстовую поставку ради числа пять и не выдавать такой fallback за полностью прошедший photo-lane. В контролируемой проверке использовать 4–5 правомерных растровых фото, чтобы реально доказать вёрстку.

### 2.6. Invariants и non-goals

Сохраняются все hard constraints, один осознанный skip, максимум пять концепций/стабильные IDs, explicit selection, оба критика, существующие six-dimension scores и UNKNOWN-интервалы, отдельные расходы/резерв/депозит, evidence authority/freshness/scope, наблюдение ≠ покупка, один принятый смысл для всех выходов.

Не добавлять: backend, provider gateway, scraper, payment/booking automation, обязательные API/MCP, multi-agent framework, новый поиск, интерактивный конфигуратор бюджета, базу медиаданных, universal document CMS, обязательный PDF, telemetry/benchmark platform. README не проходит новый дизайнерский марафон. 12 вопросных полей/5 вариантов/5 фото/фиксированное число сообщений не превращаются в обязательные квоты вопреки смыслу.

## 3. SSD

### 3.1. Архитектурная граница

`brief + intake outcome → existing Candidate/Decision + Evidence → accepted Guide/state → публикационная проверка → HTML / Поездка.md / Продолжение.md → реальный ZIP → завершение`

Облачный протокол получает правила D1/D2 явно и самодостаточно. Repo-visible agent маршрутизируется к этому же методу; наличие AGENTS.md в контексте не считается фактом прочтения travel protocol. `design-preview.html` показывает тот же шаблон на синтетических данных и не становится единственным местом новых требований.

Переиспользовать `intake.py`, `snapshot.py`, `render.py` и существующие модели/словари. Не делать второй Evidence. Свободный выбор функций, dataclass/словаря и шаблонизации — у исполнителя. Выделить небольшой HTML/CSS template из renderer допустимо, если он реально переиспользуется; один визуальный source вместо отдельного нового demo-дизайна.

### 3.2. Состояние и минимальные интерфейсы — D1

Добавить ровно столько состояния, чтобы общий intake не открывался повторно: например `intake_round=not_offered|offered|closed` на brief/run и существующие per-field unresolved. Эквивалентная более простая форма допустима. Состояние переносится в snapshot. Закрытый раунд не означает, что поля заполнены.

Новый протокол 0.2.4 валидирует не только присутствие ключей:
- canonical stage/status; publish/ready означает завершённую поставку, а не booked;
- stable run_id/revision/method_version; существующий selection_cycle;
- уникальные presented IDs включая снятые, занятых ≤5; selected_id принадлежит уже показанным;
- для PLAN/final требуется выбранный ID и реальное основание выбора;
- preset + фактические веса; сумма 100; ссылки на существующие результаты проверок и evidence;
- все hard constraints, unresolved/skip, условия дороги и исходная база бюджета;
- next_action может быть null именно при завершённой поставке; незавершённому этапу нужна точная точка продолжения;
- material delta сохраняет выбор, инвалидирует зависимое и не меняет observed_at старых фактов.

Для нового машинно проверяемого snapshot уместны YAML front matter или fenced YAML с существующим safe YAML parser плюс читаемый Markdown; это формат выдачи модели, не обязанность путешественника писать YAML. Проверять round-trip реально выданного файла, а не только исходного dict. Не строить универсальный parser произвольной прозы.

Числа, IDs, нумерация цикла и “прошедший критик” не придумываются при экспорте. Snapshot формируется из accepted state **до/вместе с render**, не восстанавливается из HTML или краткого summary. Отсутствующий критичный field должен обнаруживаться до объявления бандла полностью готовым.

Старые 0.2.0–0.2.3 не ломать. Для неполного legacy-snapshot: сохранить известный выбор/пожелания, явно описать утрату, не выдумывать прошлые IDs/веса/вердикты. Если исходный контекст доступен — адресно восстановить. Если нет — разрешено практическое продолжение, но не false `compatible/full_integrity`. При необходимости создаётся явно новая текущая ревизия после восстановления, не фиктивная история. Общий опрос не повторять. Новое строгoe правило не накладывать ретроактивно так, чтобы старый файл вообще нельзя было прочитать.

Типы/поля существующего Evidence привести к одной принятой форме на стыке writer/reader; не оставлять рабочий round-trip зависящим от “в одном месте list, в другом dict”. Scope — именно использованный путь, не общий schema-rewrite.

### 3.3. Содержание и публикация — D2

Дополнить существующий `Guide.practical_cards` и данные renderer только нужными полями. Семантический минимум карточки: stable id/topic, короткое резюме, факты с evidence refs, действия, callouts и необязательные media refs. Конкретный Python layout свободен. Если нужны `media[]`, это поле Guide, не новая база.

Минимум media record: id, section_ref, subject/scope, caption, alt, source_url, rights_basis/credit, local bytes/ref. Числа или статус по фото не выводить без отдельного evidence. `booking_tasks` остаются задачами владельца и не определяют готовность доставки.

Все виды содержат согласованные даты, числа, статусы, выбор и существенные ограничения. Подпись/картинка может отсутствовать в plain Markdown при сохранении текстового смысла и credit; пиксельное равенство не требуется. Источники — переносимые title+URL+observed_at+scope, не только native citation IDs. Scoring и findings в глубине не теряются ради красоты; отсутствующие исторические данные честно остаются missing, а не генерируются заново под лидера.

### 3.4. HTML, offline, безопасность

Сохранить текущие ENOT tokens: paper #F7F3EA, ink #183229, muted #536257, sun #EBCB63, rust #99492F, line #DCDDD2. Georgia/serif и system-ui; основной текст 16–18 px, desktop ~1120–1180 px, mobile поля ~20 px. Не копировать палитру/бренд Китая целиком.

На узком экране основные таблицы превращаются в вертикальные пары label/value или карточки. Для денег, транспорта, условий/источников и расписания не допускается требование горизонтальной прокрутки; одного `body.scrollWidth==innerWidth` недостаточно. Не “чинить” `overflow:hidden`, скрывая колонки. CSS и семантическая структура выбираются исполнителем; при двух DOM-представлениях данные генерируются из одной структуры и не дублируются для screen reader.

Содержательная навигация с короткими якорями; мобильное оглавление может быть details, не длинной горизонтальной лентой. Native details/summary, keyboard focus и текстовые статусы; смысл доступен без JS. Можно небольшой first-party JS для печати/копирования с честным fallback. Без внешних scripts/CDN/fonts/trackers.

Основной HTML содержит текст/CSS/фото автономно: предпочтительно оптимизированные JPEG/WebP/PNG внутри data URI для одного файла. Целевой размер обычного guide ≤5 MB — мягкий ориентир, не причина ухудшить читаемость. Внешние карты/продавцы/свежие цены требуют сеть, это подписано. Не выдавать внешний img URL за offline image. Все img имеют размеры/аспект; hero не lazy, остальные можно lazy; проверка прокручивает файл, чтобы убедиться в загрузке нижних фото.

Экранировать недоверенный текст. Ссылки — безопасные http/https либо внутренний anchor. Raster bytes проверяются, пользовательские SVG/HTML/JS не встраиваются как исполняемые. Не читать произвольные local paths из внешнего материала; изображения только из разрешённого каталога/предоставленного asset. Нет file:///C:/..., cookies, booking refs, passport/card данных в публичных фикстурах.

Печать — обычный browser print/CSS без собственного PDF-движка. Критичные разделы и итоги не обрезаются; глубокие блоки при печати можно раскрыть маленьким локальным handler, если это реально проверено. Не заявлять полноценный print pass без просмотра.

### 3.5. Bundle и режимы отказа

При доступной файловой среде: Путеводитель.html, Поездка.md, Продолжение.md одной run/revision + ENOT_<run_id>_rNN.zip. Проверить реальное наличие, непустое содержимое, открытие архива и состав. Старый ZIP не выдавать с новой ревизией файлов. В zip только этот выпуск и необходимые безопасные assets; не логи/личные документы/рабочая папка. Архив не должен рекурсивно включать себя.

Нет ZIP — выдать реальные три файла; нет файлов — структурированный текст+snapshot с указанием ограничения. Нет изображений — честный media fallback. Это функциональный degradation, не полная проверка premium file lane. Не заставлять путешественника запускать renderer.

Delivery-ready не означает, что браузер подтвердил скачивание/сохранение пользователем: сообщить “готово для сохранения”, не “уже сохранено на вашем устройстве”. После доставки не ждать обязательного подтверждения скачивания. Для owner-runtime release необходимо действительно доказать полноценную файловую полосу, которая в smoke была доступна.

## 4. Vertical smoke / DoD

Без нового рынка, визового ресерча и повторного планирования Краби. Предложения и выводы помечены учебными, не действующими котировками.
