# План поставки / 0.2.0 — сначала полноценный облачный путь

**Атом A0+A1 начат и не принят.** Внутренние части: сверка источников, уточнение метода 0.2.1, механические проверки. Общий вердикт исполнителя на 2026-09-30 — `AMBIGUOUS`. A2 не становится следующим шагом сам. Точный gate — чистый чат по docs/atoms/A0_A1/PILOT_PACKET.md.

Локальное приложение необязательно. Текст ниже по-прежнему описывает желаемый пилот, а не уже наблюдавшийся результат.

## Контракт будущего PRD+SSD

PRD: независимые пользователи со своими чатами; один организатор на поездку; адаптивный опрос; до пяти вариантов суммарно за цикл; явный выбор; один финальный guide; два критических прохода; суть/практика/глубина; portable handoff; отсутствие технической нагрузки на путешественника.

SSD: общий семантический контракт данных; native chat и опциональный local adapter; границы стадий/ID/ревизий; snapshot; расчёты с честным видом проверки; ссылки/оформление; экспорт в доступной форме; отсутствие скрытых зависимостей от Git, tool counters, вызова субагентов и памяти соседних тредов. Шесть моделей из CONTRACTS не требуют шести JSON-файлов в облаке. AgentPort, atomic write, localhost launch — только детали будущего local-среза.

Не проектировать свой облачный backend, мультиарендность, OAuth или marketplace Skill как prerequisite. Массовость здесь — пересылаемый starter и собственный чат каждого человека, не SaaS-инфраструктура.

## A0 — доступ к действительности в целевой среде

**Желаемая capability:** свежая, прослеживаемая подборка без подключения репозитория/специального travel-MCP.

**Consumers:** друг/родственник в облачном чате; затем автор продукта, проверяющий результат. Один сильный актуальный host — первичная среда. Второй host — тест переноса, не обязательная первая интеграция.

**Вход:** ENOT_CHAT_START.md; по желанию design-preview.html; выбранный пользователем сильный режим модели с доступным поиском. Реальный провайдер/настройки записываются как наблюдение, не фиксируются вечными версиями в blueprint.

**Проба:** один обезличенный brief на близкий отдых без автомобиля, с точными датами, двумя взрослыми, числом ночей, бюджетом на всех и veto. Конкретные даты/город — явная тестовая фактура, не угадывание личных планов владельца. Проверить чтение инструкции, получение первичных сведений о дороге/размещении, соответствие дат/состава, кэш vs актуальное предложение, работу ссылок и реальную возможность выдачи файла/архива. API не нужен, когда достаточно разрешённой страницы. Один допустимый alternate route при блокировке, затем честный gap.

**Минимальный receipt:** brief, host/наблюдаемые возможности, as-of, 2–3 material facts со scope/URL/статусом, что оказалось недоступно, путь продолжения. Без секретов и технического fingerprint. Никаких утверждений о PASS по документации вместо наблюдения.

## A1 — один законченный отдых и перенос

**Желаемая capability:** человек получает решение и организуемый план, а не презентацию возможностей модели.

Пройти тот же brief до shortlist с Critic 1. Проверить ≤5 уникальных кандидатов и отсутствие подробного guide до выбора. Выбрать один обычной фразой. Пройти PLAN и Critic 2; получить лёгкую суть, конкретный быт/возвращение, расчёты/источники в глубине и итоговый комплект. Уточнить одно условие без изменения остальных. Сохранить snapshot и начать свежий чат с ним и стартовым файлом; продолжить без исходной истории и без нового полного discovery.

### Evidence / DoD A0+A1

| Проверка | PASS для первого пилота |
|---|---|
| Старт | Человек не устанавливает инструменты и не получает требований Git/CLI/subagent |
| Этапность | Shortlist после критика, максимум 5 за цикл; PLAN только после выбора |
| Проверяемость | У важных сумм/условий дата, область и источник; кэш/оценка не выданы за наличие |
| Сохранение требований | Ни один hard constraint не исчез после правки/переноса |
| Практическая полезность | Можно назвать ближайшие действия, понятны дорога, размещение и возврат; не требуется заново искать всё основное |
| Два критика | Есть evidence-based проверка выбора и всего плана; самопроверка не названа независимой |
| Документ | Краткую суть можно прочитать отдельно; расчёты доступны глубже; существенные риски на поверхности |
| Упаковка | Реальные файлы/ZIP либо честная текстовая поставка; никакой фиктивной ссылки |
| Перенос | Свежий чат восстанавливает выбранную ревизию, ограничения, факты/пробелы и exact next |

**Бюджет пробы:** один полный сценарий + одна правка + один перенос. Рабочий потолок пилота — один активный рабочий блок владельца до 90 минут; это предложенный лимит принятия решения, не SLA модели. Не тратить новые деньги: только уже доступная среда в пределах разрешённых лимитов. Если нужен платный доступ/второй аккаунт — owner gate; ничего не покупать в обход. Время ожидания человека отделить от времени исполнения; неизвестная стоимость = unknown, не $0.

**PASS:** условия таблицы выполнены на одной финальной версии, включая настоящий чистый чат, перенос и реальные три файла, и нет скрытого дефекта, обесценивающего решение. Только после такого PASS имеет смысл отдельно решать про две другие фактуры A3. Local A2 и после PASS не обязателен и не запускается автоматически.

**FAIL:** ложная доступность, потеря veto, шестая идея/guide до выбора, фальшивый файл, или человеку приходится заново выполнять основную работу. Исправить один конкретный стык и повторить затронутую часть. Не покупать новые интеграции как автоматический ответ.

**AMBIGUOUS:** формат/процесс работает, но внешние данные заблокированы или нет возможности проверить перенос/экспорт. Зафиксировать отдельный data/delivery gap, не делать вывода «модель не справилась» и не ставить общий PASS. Следующая проба — ровно на этот пробел.

**Stop/rollback:** исчерпан лимит пробы, требуется неразрешённый доступ/расход, повторяется тот же дефект после одного repair. Сохранить результат и причину. Вернуться к последнему принятому brief/protocol revision; никаких внешних транзакций для отката нет.

## A2 — local только при доказанной пользе

Если вручную повторяются расчёты, упаковка, сохранение или проверки, добавить небольшой runner и один адаптер существующего harness. Python/Pydantic/Jinja/FastAPI — прежний кандидат, не обязательная религия. Те же смыслы, ID, snapshot и готовый визуальный язык; не другой travel engine.

Один локальный entrypoint, четыре поверхности, реальные события, безопасное сохранение, выбор/правка, экспорт. Acceptance: общие сценарии не ломаются; после падения восстанавливается принятая ревизия; нет лишней операционки. Не начинать A2 ради того, чтобы cloud перестал выглядеть «недостаточно настоящим».

## A3 — качество, переносимость и расширение без большого benchmark

Три разных запроса всего: близкая поездка, зарубежная и компания. Использовать E01–E24 по релевантности, не выполнять все комбинации платформ/сбоев. Основные новые — E15–E24 (облако, фазовая граница, экспорт, перенос, инструменты, глубина).

Сначала сравнить обычный сильный LLM-запрос и ЕНОТ на одинаковом brief и сопоставимом доступе/времени. Если есть local, сравнить его с cloud; свежие цены могут отличаться по времени, а дополнительный inventory — самостоятельный фактор, не качество мышления. Для проверки метода допустим один общий датированный evidence packet, но тогда это тест рассуждения/оформления, не live-discovery.

Не требовать одинаковый рейтинг/текст. Сравнивать потерю ограничений, unsupported material claims, полезные нетривиальные находки, ручную работу до выбора, ясность действия, практическую цельность и восстанавливаемость. **Недраматичная разница качества — гипотеза:** облако не должно систематически терять обязательный слой или требовать повторного поиска всей поездки. Один значимый успех/провал описать словами, не прятать в среднем score.

Небольшая выборка направляющая, не статистический сертификат. Если последовательный критик повторяет материальный дефект, усилить проверку evidence/контргипотезы в этом месте; не делать вторую модель обязательной для всех. Если файл создаётся, но нет layout smoke, не заявлять проверенную верстку.

## Дальше — только повторяющиеся потребности

Новый источник, API, совместное редактирование, импорт брони, уведомления — после полезных реальных прогонов. Каждый новый механизм обязан окупать свою поддержку. Массовые установки, агент на каждый день, БД всего туризма и публичный backend не входят в этот запуск.

## Команда исполнителю

> Прочитай README → AGENTS → STATE → BLUEPRINT, затем WORKFLOW, CONTRACTS и DELIVERY_PLAN. Подготовь PRD+SSD для A0+A1 cloud-first: сильная модель в обычном чате, без Git/субагентов/специальных travel-плагинов как обязательных зависимостей. ENOT_CHAT_START — самостоятельный вход. Первый цикл строго до пяти вариантов после критика и пауза до выбора; второй — один полный guide, операционный критик и реальный переносимый итог. Сохрани суть/практику/глубину, прозрачный скоринг и датированные evidence. Технические fallback не показывай путешественнику жаргоном; существенные пробелы не скрывай. Раздели общие обязанности и необязательные локальные механизмы. Зафиксируй один тестовый brief, проверки, бюджет и PASS/FAIL/AMBIGUOUS. Не требуй перед каждым безопасным подэтапом OK. Не создавай аккаунты, не устанавливай сервисы, не оплачивай и не бронируй. Результаты тестов не заменять предположением о силе модели. Синхронизируй общий метод и cloud starter в одном атоме, а локальный UI оставь отдельным необязательным усилением.
