# Контракты первого среза

Статус: **design specification 0.2.0**, не готовая библиотека схем. Семантика общая для cloud и local. В облаке эти сущности могут быть компактными Markdown-разделами; JSON, Pydantic и отдельные файлы не обязательны для путешественника. Локальная реализация переводит модели в валидируемые схемы. Не создавать противоречащие ручные версии одной истины в Markdown и JSON.

## 1. Шесть основных сущностей

| Сущность | Минимальные поля | Назначение |
|---|---|---|
| Brief | run_id, revision, locale, origin_groups, destination_scope, dates, duration_nights, party, budget, hard_constraints, soft_preferences, effort_tolerance, assumptions, unresolved | Запрос, который нельзя забыть после комментария |
| Evidence | evidence_id, claim, value, unit, currency, source_url, authority, source_family, retrieved_via, observed_at, applies_to, evidence_kind, freshness, expires_at, supports, conflicts, limitation | Что именно известно и откуда |
| Candidate | candidate_id, concept, proposed_dates, transport, lodging, anchors, cost_lines, gate_results, score_inputs, evidence_ids, tradeoffs, differentiation | Не отель, а способ провести отдых |
| Decision | brief_revision, policy_version, candidate_ids, selected_id, scoring, comparable_baseline, saving_claims, critic_result, coverage, limitations, next_action | Проверяемое основание выбора |
| Guide | decision_revision, date_range, booking_tasks, first_day, daily_plans, practical_cards, media, contingencies, return_plan, map_links, coverage, editorial_badge, evidence_ids | Единственный семантический пакет для MD/HTML |
| RunState | run_id, stage, status, active_revision, selection_cycle, presented_candidate_ids, last_valid_checkpoint, artifact_refs, usage, execution, next_action | Где продолжать; что уже было показано; фактические возможности |

Статус не должен быть зашит в имя файла. Stable ID кандидата сохраняется при изменении веса или текста; новая концепция получает новый ID.

## 2. Brief: важные детали

Даты: ISO-формат, окно допустимых выездов, фиксированная или диапазонная длительность, часовой пояс для каждого транспортного события. Отдельно число дней и ночей; поздний прилёт не создаёт лишнюю ночь автоматически. Для групп из разных городов — отдельные origin_groups с числом людей и общим ограничением места встречи.

Budget: `scope=whole_party|per_person`, `currency`, `target_amount`, `hard_cap`, `included_categories`, `reserve_policy`. После нормализации сравнение проводится в одной базе; исходный ввод сохраняется. Валютный пересчёт имеет источник/дату и не прячет комиссии. В машинном расчёте деньги — Decimal либо минимальные единицы валюты, не binary float. В чате без вычислителя обязательны единицы, количества и явная сумма; сложный неподтверждённый расчёт остаётся оценкой/диапазоном. Отсутствие калькулятора не превращает текстовый подсчёт в machine-verified.

Party: взрослые, возраст детей, необходимое число кроватей/комнат, допустимо ли делить жильё/перелёт, функциональные ограничения. Не нужны полные имена, номера документов, диагнозы и платёжные реквизиты.

Hard constraint имеет `id, requirement, origin=user|policy, applicability, must_pass`. Смягчение пользовательского veto возможно только через явное изменение brief. Дефолт не превращается в согласие на самостоятельный транзит.

`intake_round=not_offered|offered|closed` и `intake_outcome=not_offered|offered|sufficient|answered|skipped` — состояние одного optional раунда. Закрытие не означает заполненность. При частичном ответе и просьбе продолжать предложенные неизвестные сохраняются null/user_skipped. Новый material scope может потребовать один адресный вопрос, не второй общий intake.

`unresolved` — список материальных пробелов (выполнимость и попадание в желаемый отдых), не вторая анкета. У элемента: `field`, `clarification_status=needs_input|offered_once|user_skipped`, `impact`. Пропуск не получает выдуманное значение и не становится допущением. В том же scope и в новом чате со снимком вопрос с `user_skipped` не повторяется. Повторно спрашивается только одно поле, если новый scope или точный claim без него невозможен. Опрос в облаке остаётся обычным текстом.

## 3. Evidence: тип, свежесть и полномочие — разные поля

`evidence_kind`: `primary_fact | observed_offer | cached_price | estimate | anecdote | user_report`.

`freshness`: `current_for_scope | stale | unknown`. Календарная свежесть не даёт источнику полномочий. Новый блог всё ещё не официальный визовый источник. Старое наблюдение о расположении не обязательно устарело; старое предложение билета почти всегда требует новой проверки.

`applies_to` для цены: даты, маршрут/объект, полный состав, комнаты, багаж, питание/тариф, рынок/валюта, включённые налоги и сборы. Отсутствующее поле явно null/unknown, не выдуманный default.

`expires_at` поставщика сохраняется без изменений. Если срока нет, система задаёт момент необходимого recheck по политике, но не изобретает «гарантирован до». В каждой карточке видна дата наблюдения. При открытии архивного статического HTML видна его дата и предупреждение, что данные не обновляются автоматически.

Критичное утверждение содержит `evidence_ids`. Неподтверждённое утверждение получает `estimate`/`unknown` и ограничения. Источники с общим source_family не считаются независимыми голосами. Короткие извлечения/атрибуция допустимы; сохранять чужие платные путеводители целиком не нужно.

## 4. Gate и состояние кандидата

Gate: `PASS | FAIL | UNKNOWN | NOT_APPLICABLE`. Для FAIL/UNKNOWN — последствие и конкретное следующее действие. NOT_APPLICABLE требует причины, например «визы: поездка внутри страны».

Derived state: `verified_for_decision | conditional | rejected`. Это **не** `booked`.

`verified_for_decision` требует отсутствия FAIL и критичного UNKNOWN, плюс применимых подтверждений для материальной дороги/жилья/размещения. Не все бытовые цены обязаны быть котировками: пример меню может быть estimate, но критичный unknown в общей сумме должен менять допуск/интервал бюджета.

`conditional` можно показать отдельно, без награды «проверенный лучший». `rejected` остаётся в аудите с причиной. Не блокировать весь run из-за одного кандидата, если есть другие.

## 5. Полный бюджет и сравнение

Каждая cost_line: `category, quantity, unit, base_amount, currency, scope, lower, upper, included_in, mandatory, evidence_ids, kind`. `included_in` предотвращает повторный подсчёт пакета, завтрака или трансфера.

Раздельно: обязательные известные траты; обычные оценочные расходы; contingency reserve; возвратные депозиты/holds. Итог расхода включает резерв согласно brief. Депозит увеличивает cash_needed, но не travel_spend. Риск невозврата депозита раскрывается отдельно.

Если полный бюджет является диапазоном: `upper <= hard_cap` — проходит финансовое условие; `lower > hard_cap` — не проходит; интервал пересекает hard_cap — conditional, пока не уточнены сумма или лимит. Не использовать нижнюю границу для ложного PASS.

`savings_pct = (baseline_total - candidate_total) / baseline_total * 100`, только когда baseline_total > 0 и обе корзины действительно сопоставимы по датам, составу и основным услугам. Для диапазонов публикуется обоснованный диапазон экономии либо отказ от процента. Сравнение только цены отеля — не экономия всей поездки.

## 6. Скоринг

Шесть измерений и веса — config/policy.yaml. Шкала 0–5, разрешены половинные значения. Якоря общие: 0 = противоречит желанию; 1 = слабое соответствие; 3 = приемлемо с понятным компромиссом; 5 = сильное соответствие без значимого компромисса в этом измерении. 2 и 4 — промежуточные состояния.

Уточнение по измерениям:

| Критерий | 1 | 3 | 5 |
|---|---|---|---|
| fit | Почти другой тип отдыха | Основное желание выполнено | Желание и ограничения хорошо согласованы |
| value | Заметно уступает сопоставимой альтернативе | Разумный обмен цены и набора услуг | Обоснованно сильная ценность на полном бюджете |
| logistics | Утомительная/хрупкая организация | Допустимые переходы и хлопоты | Простая дорога и мало организационных действий |
| comfort | Нужные бытовые качества слабы | Базовый комфорт выполнен | Комфорт соответствует именно этой компании |
| novelty | Уже надоевшее/неинтересное | Есть значимое новое | Сильный желанный новый опыт, а не редкость ради редкости |
| flexibility | Трудно отменить/перестроить | Есть ограниченные замены | Существенные элементы гибкие и есть запасные решения |

Каждое измерение: score|null, rationale, evidence_ids, uncertainty. Низкий hard gate нельзя компенсировать баллами.

`S = Σ(w_i * s_i / 5)`; веса в процентах, сумма ровно 100. При пропуске ненулевого критерия `score_interval=[known_sum, known_sum + Σ(missing_weights)]`. Нельзя ранжировать такой диапазон как точечный балл. Критерий веса 0 не влияет на сумму и допускает null. Значительные интервалы/пересечение лидеров переводят вывод в «нужно уточнить» или «варианты близки».

Sensitivity при вычислителе: каждый ненулевой вес отдельно изменить на ±20% относительно него, остальные пропорционально перенормировать до 100, повторить ранжирование с фиксированными score_inputs. Это диагностическая политика, не статистическая доверительная вероятность. Без вычислителя допустима качественная проверка зависимости выбора от весов; `sensitivity_execution=qualitative`, не «расчёт подтвердил устойчивость». Данные/баллы нельзя подправлять для сохранения любимого лидера.

Для чисел хранить `calculation_check=tool_verified|explicit_arithmetic_review|unverified` и отдельно основание исходных величин. Проверенная арифметика не делает оценочную цену предложением. При unverified не публиковать точный процент экономии/ложную точность лидерства. Безмашинный путь не отменяет формулу, сумму весов, интервалы и право пользователя менять параметры.

Редакционная медалька хранится отдельно: `enots, band, rationale[2..3], limitation, assessor, assessed_at`. Число 0–100 — субъективная оценка целостности опыта. Оно не вычисляется из тех же весов и не заявляет измеренную точность. Публикация только после пройденных материальных проверок; в design-demo — явная синтетическая маркировка.

## 7. Этапы и безопасное продолжение

Stage: `brief | discovery | verification | decision_review | selection | planning | operational_review | publish`.

Status: `draft | running | needs_input | ready | partial | failed | cancelled`.

Stage — что делаем; status — состояние работы. `ready` означает готовность этапа, не купленную поездку. Freshness принадлежит evidence. Пользователю эти поля передаются обычным языком.

**Завершение:** publish/ready/next_action=null после согласованной реальной поставки; booking_tasks принадлежат владельцу. Покупка, будущий recheck и согласование позднего заезда при бронировании не держат чат needs_input. Known hard FAIL исключён; critical UNKNOWN и его последствия видны в первом слое, условный план не называется полностью пригодным. Нет обязательного возврата с ответом продавца и фонового мониторинга.

**Граница выбора:** после Critic 1 `stage=selection`, `status=needs_input`, `selected_id=null`; PLAN требует явного выбора. Рекомендация, сравнение двух и отрицательное упоминание ID не являются выбором. «Продолжай» при частичном DISCOVER не является выбором лидера. Неясный, устаревший или неоднозначный ID не открывает PLAN: задаётся только уточнение выбора. Не создавать guide до выбора только потому, что остался бюджет хода. После смены даты или состава прежний `selected_id` сохраняется с `requires_revalidation`; другая концепция не подставляется. Пока перепроверка не закончена, затронутые условия не публикуются как свежие.

**Пять суммарно:** в каждом `selection_cycle` множество `presented_candidate_ids` имеет не более 5 уникальных элементов, включая conditional и предложения в разных сообщениях. Повторное описание того же ID не новый кандидат. Удаление или скрытие карточки не удаляет ID из этого множества и не освобождает слот. Новая концепция имеет новый ID, в том числе в следующем цикле. REFINE по комментарию может создать новый цикл и новый набор, а не незаметно увеличить старый до десяти. Сохранять, какие прежние варианты исключены и почему.

Имена этапов PRD `INTAKE / DISCOVER / CRITIC_1 / WAIT_SELECTION / RECHECK_SELECTED / PLAN / CRITIC_2 / PUBLISH` не образуют вторую машину состояний. Им соответствуют уже заданные `brief`, `discovery`+`verification`, `decision_review`, `selection` при `needs_input`, начало `planning` с pending recheck, `planning`, `operational_review`, `publish`. `REFINE` — новая ревизия brief. `PAUSE` и `RESUME` — snapshot и возврат в тот же stage после повторной оценки возможностей среды.

Finding критика: `severity=BLOCKER|MATERIAL|POLISH`, проблема, evidence, последствие, объект, минимальное исправление, результат recheck. Один material repair на пользовательский checkpoint. Самопроверка той же моделью не называется независимым аудитом.

Final 0.2.4 сохраняет достигнутые `guide`, рассчитанный `budget` со строками и `scoring` всех показанных вариантов с основаниями/результатами. Практика содержит применимые facts/actions/callouts, а не только заголовки. Нет универсального числа карточек или фактов. `booking_tasks` содержит действия, сроки и последствия; когда действий нет по смыслу поездки, это объясняет `booking_tasks_not_applicable`, видимый в guide. Утрата достигнутого содержания блокирует full_integrity и production export; ранние этапы и честное чтение legacy не требуют ещё не созданного финала.

Critic `REPAIR` не допускает publish/ready. Исторический `BLOCKER` требует `resolution=resolved` и `recheck={status: PASS, summary: содержательный результат, evidence_ids: существующие IDs}`; после исправления verdict обновляется. `PARTIAL` с явными условиями и без нерешённого BLOCKER допустим. Условное намерение или отозванный выбор не является основанием PLAN. Локальный парсер распознаёт ограниченные прямые формы выбора и блокирует известные неоднозначности; смысл всей реплики проверяет основной LLM protocol, сомнение требует адресного уточнения.

В каждом checkpoint: revision, stage/status, принятые результаты, timestamp если известен, пробелы и точное next_action. Cloud: сохранить в доступном артефакте/снимке или в видимом тексте. Local: один writer/lock, атомарный rename, task_id, контроль входной ревизии и неизменяемые принятые выходы. Эти filesystem-механизмы не требуются в обычном чате.

REFINE: даты → transport/lodging/events/rules/budget; состав → transport/lodging/activities/budget; веса → scoring/readout; стиль → text/render; усталость → day plans/logistics/anchors. Дизайн не запускает поиск билетов. Новые даты не наследуют старую доступность.

Snapshot — видимое краткое состояние и факты, не chain-of-thought и не стенограмма. После утраты контекста нельзя восстановить точные ограничения/источники из догадки; прочитать сохранённое или задать один действительно необходимый вопрос.

## 8. Переносимый результат и локальное хранение

### 8.1. Идентификация

`run_id=YYYY-MM-DD_short-query-slug_NN`, например `2026-09-29_les-voda-dva-dnya_01`. Дата — запуск, не отпуск. Русское название хранится внутри. Ревизия `r01`, `r02` меняется при изменении принятых сведений; время наблюдения источника от этого не обновляется. Один run не переименовывается при переносе в другой host.

### 8.2. Общий итог для путешественника

```text
ENOT_<run_id>_rNN.zip
  Путеводитель.html
  Поездка.md
  Продолжение.md
```

Это **будущий результат конкретной поездки**, не состав проектного starter ZIP. Стартовый файл ENOT_CHAT_START и дизайн-образец — метод и эталон, а не реальные брони.

`Поездка.md` — принятое содержание: лёгкое резюме, запрос/выбор, практика, источники/скоринг/проверки в глубине. HTML — оформление тех же сведений. `Продолжение.md` — компактный снимок выбранных полей этой ревизии; не параллельная база цен и не весь raw corpus. В пределах одного выпуска revision/run_id совпадают. При конфликте восстановить последнюю **принятую** ревизию, не выбирать по красивому имени; неразрешённый конфликт критичных условий требует уточнения.

При наличии файлового инструмента проверить существование и содержимое файлов; создать ZIP и дать реальную ссылку на HTML/архив. При отсутствии упаковки выдать реальные отдельные файлы. При отсутствии файлов — те же разделы текстом в чате и snapshot; `delivery=text_in_chat`, не `zip_created`. Не заставлять обычного путешественника запускать сборочный скрипт. Рисованный «Download» без реального действия запрещён.

### 8.3. Минимальный snapshot

В одном Markdown-разделе/файле:
- run_id, русское название, revision, версия метода, selection_cycle, stage/status, дата сохранения;
- нормализованный brief целиком в краткой форме: откуда и возврат, даты и длительность, состав и размещение, база бюджета, желаемая сумма, потолок и валюта, все veto, мягкие пожелания, допустимые хлопоты, допущения и `unresolved`, включая `user_skipped` без подставленного значения;
- preset/изменённые веса, все presented_candidate_ids цикла, включая снятые, с краткими отличиями, число занятых слотов, selected_id, явное основание выбора и `requires_revalidation`, если правка затронула выбранное;
- факты, от которых зависит выбор: значение/единица, URL/источник, дата получения и применимость, статус/пробел; ссылки не только внутренние маркеры чата;
- что уже принято, результаты двух проверок по достигнутым этапам, нерешённые материальные вопросы;
- что перепроверить при возобновлении, точный следующий шаг и при необходимости одно сообщение продолжения;
- сведения о доступных артефактах и фактическом способе проверки без секретов.

Снимок после shortlist не обязан содержать ещё несуществующий guide. Практический ориентир объёма — 500–1200 слов, **не hard cap**: ограничения не выбрасываются ради длины. После большой правки или длительной паузы snapshot обновляется; ручное вмешательство пользователя в файлы не требуется.

Snapshot 0.2.4: fenced YAML + читаемый Markdown, сериализованный файл проверяется safe YAML reader. Проверяются типы/enum, run/revision/method, полный compact brief/constraints/intake, preset/веса (шесть измерений, сумма 100), уникальные ID ≤5 с краткими концепциями и withdrawn, выбор/реальные слова пользователя, evidence refs, достигнутые critics, invalidation и next_action. Evidence на writer→reader пути — список существующей формы Evidence; legacy mapping допустим при invalidation. Snapshot создаётся из accepted state, не HTML/памяти. Новый final включает проверенный delivery receipt.

Legacy 0.2.0–0.2.3 читается без ретроактивного запрета. `compatible` старой формы не означает `full_integrity`: потерянные IDs/weights/critics явно missing, известный выбор сохраняется без выдуманной истории. При доступном старом state восстановить адресно; иначе practical continuation и одна новая текущая ревизия после восстановления. Общий intake не повторять.

### 8.4. Локальное расширение, не обязательный формат облака

```text
research/<run_id>/
  state.json
  brief.json
  candidates.json
  evidence.jsonl
  events.jsonl
  revisions/01/
    decision.json
    shortlist.md
    critic.json
    guide.json
    guide.md
    guide.html
    resume.md
```

Ревизия содержит только достигнутые результаты. Локальный `guide.json` — канонический пакет реализации; `guide.md` и HTML — его views. Cloud при наличии кода тоже может использовать структурированный пакет; без кода источником принятого смысла является одна явно фиксированная текстовая версия, не новая генерация «по памяти» для каждого формата. Snapshot и финальный экспорт создаются из неё.

Весь research исключён из Git. Индекс локальных поездок — только при реальной потребности поиска; персональная память — opt-in. Перед внешней передачей убрать имена/номера документов/коды/приватные ссылки. Не публиковать поездки через публичные страницы по умолчанию.

### 8.5. Самостоятельные ссылки и проверка упаковки

У material claim переносимые references: читаемое название, публичный URL или указанное пользовательское свидетельство, дата, точная поддерживаемая часть. Native citations в чате можно сохранить дополнительно, но они не единственная опора экспортированного файла. Не выдумывать дату/секунды наблюдения, когда известен только день.

Экспорт не вызывает новое исследование автоматически. Проверить совпадение сумм, дат, статусов, выбранного варианта и ссылок; HTML без внешнего кода/трекеров. Machine render/валидатор предпочтителен при доступности; иначе `render=assisted_checked`, а не притворный deterministic proof. Браузерный визуальный тест заявляется только после реального выполнения.

## 9. Локальная граница AgentPort / ProviderPort

Эти интерфейсы относятся только к локальной реализации. Обычный облачный чат не обязан предоставлять API, callbacks или tool receipts такой формы.

AgentPort принимает узкий TaskEnvelope: task_id, objective, brief_revision, allowed_inputs, expected_output, allowed_tools, call_budget, deadline, repair_budget. Возвращает структурированный результат и статус, не произвольный текст как единственный контракт.

ProviderPort возвращает `ok|unsupported|blocked|rate_limited|unavailable`, данные и причину. `ok` на уровне транспорта не равен проверенным evidence. Технология доступа — connector/API/browser/manual — сохраняется отдельно от полномочия первичного источника.

Host ограничивает права: только необходимые чтения/поиск; исследования не меняют код/политику и не бронируют. Выходы агента валидируются и записываются host в папку run. Если выбранный harness не может реально обеспечить нужную изоляцию, это явный пробел A0, а не обещанная безопасность из текста prompt.


## 10. Внутренняя карта исполнения и равенство смысла

В RunState `execution` содержит по необходимости: host label если известен, возможности поиска/вычисления/файлов/делегирования/сохранения (`available|unavailable|unknown`), review_execution, calculation_check, render_check, delivery. Не хранить cookies, credentials и подробный fingerprint. Не создавать ради этого отдельный сервис/реестр. Путешественнику не показывать механические поля, если он не запросил аудит; показывать их последствия для решения.

Общие обязанности: ограничения, альтернативы, evidence, all-in, критерии/веса, две критические проверки, этап выбора, семантический guide, snapshot. Условные механизмы: subagent, Git, JSON, shell, ZIP, Jinja. Отсутствие условного механизма не отменяет обязанность; отсутствие самой проверяемой информации не может быть скрыто имитацией.

Локальные лимиты tool calls и concurrency применяются, только когда host их действительно считает/контролирует. В обычном чате — ограничение scope/глубины и реальные лимиты среды; неизвестные длительность, tokens и стоимость записываются null/unknown, не нулями. Не обещать фоновый worker, переносимость внутренних citation IDs или доступ к соседним тредам.

## 11. Owner-ready Guide / 0.2.4

Один accepted Guide в state питает HTML, Поездку и snapshot. Local seam `content_from_snapshot` берёт Guide, identity, выбор и бюджет из этого state. Writer проверяет совпадение и арифметику, сериализует, открывает ZIP и только после readback возвращает ready. Новый snapshot сохраняет практику и owner tasks для адресного Q&A.

Карточка: stable id/topic, summary, facts (label/value/status/evidence_ids), actions, callouts (important/tip/fallback, text/status/evidence_ids). Media привязаны к section_ref. Статусы known/estimate/UNKNOWN/owner_action/future_recheck отделены от оформления. Материальные детали: что/где/когда → действие → деньги/включённость → ограничение/fallback → evidence/scope. Это семантика, не обязательные пустые поля. Critical UNKNOWN выводится в summary; hard FAIL запрещает пригодную выдачу.

Media: id/section_ref/subject/scope/caption/alt/source_url/rights_basis/credit/asset. Только разрешённые raster assets из явно одобренного caller directory: verify/re-encode JPEG/PNG/WebP, убрать EXIF. SVG/HTML/JS, arbitrary path, symlink escape и unsafe URL запрещены. Обычно 4–5 различных фото; отсутствие прав/байтов — явный media fallback, не полный photo PASS. Депозит null сохраняет cash_needed null; расход и резерв отделены от ликвидности.

HTML offline с embedded photos/CSS, no-JS чтение, native details и focus. Основная мобильная информация — label/value, без внутреннего горизонтального scroll и скрытых колонок. ZIP текущей ревизии содержит ровно три непустых выхода, без старых файлов, секретов и самого архива. Readback сверяет bytes и actual YAML snapshot.
